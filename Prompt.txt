## 1. The problem
A git repository's tree can contain things that are dangerous or broken once checked out: symlinks with absolute, escaping or Windows network (UNC) targets; entries that sit BEHIND a symlink in the same tree (a path component that is a symlink, followed by files beneath it); names that Windows/macOS filesystems treat as `.git` or other special names; suspicious submodule URLs. On Windows, where `core.symlinks` is false by default, every committed symlink becomes a plain text file containing the target path, silently breaking projects that rely on them. Developers cannot easily inspect these things BEFORE checkout. safetree inspects the committed tree (without checking anything out) and also detects symlinks that were already checked out as text stubs. Read-only, offline for local repos.

## 4. Behaviour (MVP)
CLI: `safetree [path]` audits a local repository; `safetree inspect <url-or-path>` performs a safe pre-checkout audit of a remote repository; programmatic API.
Data gathering (read-only; execFile with argument arrays, `shell: false`, timeouts, max buffers, `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0`; paths always passed after `--`):
- list the tree of a revision (default HEAD, option `--rev`) with `git ls-tree -r -z --full-tree`; parse NUL-separated records robustly (names may contain newlines, tabs, quotes, invalid UTF-8; handle as Buffers and escape for display);
- read the blob content ONLY for mode 120000 entries (symlink targets) and for `.gitmodules`, via `git cat-file --batch`, with size caps;
- for the working tree stub check: `git ls-files -s -z` plus lstat of the working file.
Rules (each finding: id, severity, title, evidence, why it matters, suggested next step labelled "verify before running"; keep only rules that survived Phase 0):
- ST001 (error): symlink with an absolute target (POSIX `/...` or Windows drive `C:\...` / `C:/...`).
- ST002 (error): symlink target that is a UNC/network path (`\\host\share`, `//host/share`, `\\?\UNC\...`). Explain the credential-leak risk and cite the Git for Windows security advisory you verify in Phase 0.
- ST003 (error): symlink target that resolves OUTSIDE the repository root (lexical resolution relative to the symlink's directory; treat both `/` and `\` as separators and flag mixed separators).
- ST004 (warn): symlink target does not exist inside the same tree (dangling) - lexical check against the tree listing.
- ST005 (warn/info): Windows impact report: number of symlinks, list (capped), and which of them are files vs directories (when determinable), explaining that with `core.symlinks=false` each becomes a text file. Higher severity when the symlink path looks like source code, a license, a config or a package manifest (documented extension list).
- ST006 (error): "entry behind a symlink": any tree path whose parent directory component is itself a symlink entry in the same tree (for example `a` is a symlink and `a/hooks/post-checkout` exists). Deterministic tree analysis. Also detect case-insensitive variants of this pattern.
- ST007 (error/warn): path components that Windows or macOS filesystems may treat as `.git` or other protected names: use ONLY the list verified in Phase 0 from Git's own protectNTFS/protectHFS documentation/source (for example case variants, trailing dots/spaces, 8.3 short names, ignorable Unicode on HFS+); flag in paths and in symlink targets.
- ST008 (warn): suspicious `.gitmodules` entries: URLs using the `ext::` transport, `fd::`, a leading `-`, control characters, or `file://`/local paths; `path` values with `..` or absolute paths; `.gitmodules` that is itself a symlink. Simple line-based parser (no INI library), labelled low-confidence where heuristic. Never fetch submodules.
- ST009 (warn): case-insensitive or Unicode-normalization (NFC/NFD) collisions where at least one of the colliding paths is a symlink or a directory prefix of another path (on case-insensitive filesystems the checkout would merge or redirect them).
- ST010 (error, working-tree mode): an entry that is a symlink in the index (mode 120000) but is a regular file in the working tree (text stub from `core.symlinks=false`), shown with the stub's content.
- ST011 (info): summary: counts of symlinks, executables (100755), submodules (160000), total entries, largest directories.
`safetree inspect <url>`: validate the URL strictly first; then `git clone --no-checkout --no-tags --depth 1 --no-recurse-submodules --template=<empty temp dir> --config core.hooksPath=<empty temp dir> -c core.fsmonitor=false -c protocol.ext.allow=never --` into a fresh temp directory with 0700 permissions, run the tree audit on it, print results, ALWAYS delete the temp directory (even on error, SIGINT/SIGTERM; `--keep` retains it for debugging with a printed warning). Never run checkout, never run hooks, never run any command inside the clone other than the read-only plumbing above. Set `GIT_ALLOW_PROTOCOL` to a restrictive list (https, ssh) plus `file` only when `--allow-local` is passed. Document that this command uses the network and the user's configured git credentials, and that a malicious server could still serve a hostile repo, which is exactly why no checkout happens.
Options: `--rev <ref>`, `--format human|json|github|sarif`, `--fail-on error|warn|never` (default error), `--max-entries` (default 1,000,000), `--no-color`, `--config`.
Config (optional `.safetreerc.json`, strict schema validation): `ignore` paths/rules each with a required reason, `failOn`, `maxEntries`.
Exit codes: 0 clean, 1 findings at/above `--fail-on`, 2 usage/runtime error (not a git repo, git missing/too old, ownership refusal: report clearly and NEVER add safe.directory automatically, URL rejected, clone failed).
Display of repo-controlled bytes: ALWAYS escape control characters, ANSI sequences, newlines and invalid UTF-8 (show as \xNN or \u{...}) so a hostile file name cannot forge output lines.

## 5. Security requirements (implement AND test)
- Repositories and remote servers are UNTRUSTED input. Never check out, never execute hooks, scripts, filters, textconv, or any repo-controlled program. Disable what you can on every git call: `-c core.fsmonitor=false`, `-c core.hooksPath=<empty>`, `-c protocol.ext.allow=never`, `GIT_TERMINAL_PROMPT=0`, and verify each setting exists in the minimum supported Git version (Phase 0).
- URL validation for `inspect`: reject URLs starting with `-`, containing control characters or whitespace, using `ext::`, `fd::` or unknown transports; accept only https, ssh (including scp-like `user@host:path`), and local paths only with `--allow-local`. Always pass the URL after `--`. Test that option-injection strings (for example `--upload-pack=...`) and `ext::sh -c ...` are rejected and execute nothing (use harmless marker files that must NOT appear).
- Use execFile/spawn with argument arrays, `shell: false`, timeouts, max output buffers; kill the process tree on timeout. Never `exec`. Never interpolate repo-controlled strings into commands.
- Resource limits: max tree entries, max blob bytes read for symlink targets (symlink targets over 4096 bytes are flagged and truncated), max `.gitmodules` size, max findings stored, bounded recursion/iteration; all regexes linear-time with adversarial tests.
- Temp directories: created with restrictive permissions, unique names, always cleaned up (including on crash paths where possible); never reuse predictable names.
- Output hygiene: escape control characters for terminals; escape GitHub workflow commands (%, \r, \n, ::), SARIF and JSON; report repo-relative paths only (no absolute local paths; home directory shown as `~` if ever needed).
- Strict config validation; prototype-pollution safe (Map / Object.create(null)); no eval/Function; no dynamic require of user input.
- SECURITY.md with private vulnerability reporting via GitHub Security Advisories.
- Supply chain: no runtime deps, `npm audit` clean, lockfile committed, GitHub Actions pinned to commit SHAs with least-privilege `permissions:`, Dependabot (actions + npm), CodeQL workflow, publishing via GitHub Actions with `--provenance`, `"files"` allowlist (verify with `npm pack --dry-run`).
